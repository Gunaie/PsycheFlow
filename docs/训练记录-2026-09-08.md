# 训练记录：dialog/report LoRA 反模板重训（2026-09-08）

## 一、训练目标

解决本地 7B LoRA 模型对话回复的**模板腔**与**封闭式问句**问题：
- 模板腔："我理解你的感受""这一定让你感到很疲惫""听起来你最近过得很辛苦"等套路开头
- 封闭问句：以"对吧/对吗/是不是/好吗"结尾，无法引导来访者继续表达

## 二、训练环境

| 项目 | 配置 |
|---|---|
| 云平台 | AutoDL，RTX 4090 24GB，数据盘 50GB |
| 基座 | Qwen2.5-7B-Instruct（ModelScope 下载，15GB） |
| 微调框架 | LLaMA-Factory 0.9.5，transformers 4.57.6，torch 2.8.0+cu128 |
| 方法 | QLoRA：4bit 量化基座 + LoRA（rank=32, alpha=64, dropout=0.05, target=all） |
| 可训练参数 | 40,370,176 / 7,655,986,688 = **0.5273%** |

## 三、训练数据

合并后 **1386 条**（`data/dialog_merged.jsonl`），每条注入 318 字符 system prompt：

| 来源 | 条数 | 说明 |
|---|---|---|
| DeepWell-Adol 清洗后 | ~600 | convert_deepwell.py：剔除模板腔/封闭问句样本 |
| 云端合成 | 500 | gen_samples_cloud.py：qwen3.8-max 生成，100 场景 × 5 组 |
| DeepWell 改写 | ~280 | rewrite_deepwell.py：保留原 human，云端 LLM 改写不合规 gpt |

report 数据 52 条（`finetune_report.jsonl`，评估结果 → 发展建议）。

**system prompt 核心约束**：共情但不套话；50-100 字 ≤3 句；开放式追问结尾；不评判不说教；危机敏感（12355/120/110）。

## 五、踩坑记录与修复（按发生顺序）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `tail: train.log: No such file` | 先 tail 后 nohup，顺序反了 | nohup 启动后再 tail |
| 2 | `pip install openai` 报 No matching distribution | 学术加速代理（network_turbo）开着，国内 pip 源被代理坏 | pip 前 `unset http_proxy https_proxy ...` |
| 3 | [2a] 未跳过，重复生成合成样本 | synthetic_dialog.jsonl 上传到 `ft/` 而脚本检查 `ft/data/` | 拷到 data/ 目录 |
| 4 | `ModuleNotFoundError: openai` | [2a] 跳过后其内部的 pip install 没执行，[2b] 依赖 openai | pip install openai 移到 [2a] 之前无条件安装 |
| 5 | `ValueError: Your setup doesn't support bf16/gpu`，torch 为 `2.8.0+cpu` | pip 装 llamafactory 时阿里云 PyPI 源的 CPU 版 torch 覆盖了镜像 CUDA 版 | cloud_train.sh 加自动检测：无 CUDA 则开代理从 pytorch 官方 cu128 源重装 |
| 6 | cu128 重装后仍是 `2.8.0+cpu False` | `pip install torch==2.8.0` 认为已装的 +cpu 版满足版本号（本地标记 +cpu/+cu128 不参与匹配），未实际下载 | **先 `pip uninstall -y torch torchvision torchaudio` 再装**，加 `--no-cache-dir` |
| 7 | 导出合并模型时 `No space left on device` | 50GB 数据盘：基座 15G + merged 15G + f16 15G + 旧训练残留，峰值超限 | 50GB 结构性不够（峰值理论 ~54G），**数据盘扩容到 100GB**；脚本侧同步优化：转完 f16 立即删 merged、训练后自动清 checkpoint |
| 8 | convert 报 `TypeError: expected np.ndarray (got memmap)` | **双 numpy 副本**：gguf 依赖链装 numpy 2.x、降级 1.26.4 时装到另一 site 目录，torch C 层 `PyObject_TypeCheck` 持有的 `PyArray_Type` 与实际数组来自不同 numpy 安装，memmap/普通 ndarray 均被拒 | 连卸两次 numpy + 物理删两个 site 目录的 numpy 残留 + 重装 1.26.4；脚本 [6/6] 开头加 `torch.from_numpy` 自检自愈 |
| 8b | （误判弯路）`.view(np.ndarray)` 补丁 | 一度以为是 memmap 子类被精确类型检查拒绝，加了 view 补丁后报错变为 `got numpy.ndarray` 才暴露真因是双 numpy | view 补丁保留（幂等无害）；脚本 [5/6] clone llama.cpp 后自动打补丁 + 显式 pin `numpy==1.26.4` |

**所有脚本侧修复已固化进 [cloud_train.sh](../backend/scripts/finetune/cloud_train.sh)**，重跑/下次训练自动生效：
- torch CUDA 自动检测修复（检测到 CPU 版自动开代理重装 cu128，且先 uninstall 再装避免版本号陷阱）
- openai 无条件安装 + pip 前关代理（学术加速与国内 pip 源互斥）
- llama.cpp clone 后自动打 memmap 补丁 + 显式 pin `numpy==1.26.4`
- [6/6] 转换前 numpy 自检自愈（双副本检测 → 连卸 + 物理清残留 + 重装）
- 训练后自动清 checkpoint-*
- merge_and_gguf 流水线（f16 转完立即删 merged，峰值空间 ~54G → ~35G）
