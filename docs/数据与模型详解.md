## 一、数据全景概览

项目数据分为 **6 大类**：

| 数据类别 | 来源 | 存储位置 | 用途 |
|---|---|---|---|
| 知识库语料 | 内部编写 + 公开资料整理 | `data/knowledge/*.txt, *.md` | RAG 检索 |
| 量表题项与规则 | 国际通用量表本土化 | `backend/app/scales/` | 规则化计分 |
| 对话训练数据 | DeepWell-Adol + 云端合成 | `data/finetune/dialog_merged.jsonl` | dialog LoRA 微调 |
| 报告训练数据 | 项目测评数据 + 云端蒸馏 | `data/finetune/finetune_report.jsonl` | report LoRA 微调 |
| 评估测试数据 | 人工标注合成 | `backend/scripts/eval/` | 模型评测 |
| 运行时业务数据 | 用户使用产生 | SQLite `data/psycheflow.db` | 会话/对话/测评/审计 |

### 2.2 元数据规范

每个文件头部包含两行元数据：

```
来源：内部编写，基于XX整理（科普用途，不构成诊疗建议）
适用场景：焦虑,放松
```

- `来源：`：标注数据出处，用于溯源
- `适用场景：`：受控词表标签，用于 RAG 检索过滤

**受控词表**：危机、焦虑、放松、睡眠、抑郁、诊断、科普、CBT、DBT、情绪、沟通、共情、评估

### 2.3 数据处理流程

代码：`backend/app/rag/service.py`

```
原始 .txt/.md 文件
    │
    ▼
parse_metadata() ── 剥离「来源：」「适用场景：」行，提取标签列表
    │
    ▼
chunk_text() ── 结构感知切片
    │   ├── Markdown 标题作为【章节】前缀
    │   ├── 过短段落（<10字）丢弃
    │   ├── 缓冲 <40字 并入相邻段
    │   └── >400字 按句子边界二次切分
    │
    ▼
load_corpus() ── 生成 [{id, text, source, tags}]
    │
    ▼
build_index() ── text-embedding-v3 向量化 → 写入 Chroma（metadata 含 tags）
```

**切片参数**：
- `MAX_CHUNK_CHARS = 400`：单片正文上限
- `MIN_CHUNK_CHARS = 40`：缓冲下限
- `MAX_SECTION_PREFIX = 40`：章节前缀截断长度

## 三、量表测评数据

### 3.1 四套量表

目录：`backend/app/scales/`

| 量表 | 文件 | 题数 | 评分范围 | 界值 |
|---|---|---|---|---|
| PHQ-A | phq_a.py | 9 题 | 0-27 | ≥11 阳性 |
| SCARED | scared.py | 41 题 | 0-82 | ≥25 阳性 |
| SDQ | sdq.py | 25 题（含 5 道反向计分） | 0-40 | 16-19 边缘，≥20 异常 |
| MHT | mht.py | - | - | - |

### 3.2 计分引擎

代码：`backend/app/scales/base.py`

**设计原则**：计分纯规则化，绝不进 LLM，确保确定性与可审计。

**数据结构**：
```python
ScoreResult:
  scale_id, scale_name, total_score, severity
  crisis_level (SAFE / ELEVATED)
  crisis_triggers (触发危机的题项描述)
  factor_scores (因子分 dict)
  interpretation
```

**关键规则**：
- 缺题、题号越界、分值非法均抛 `ValueError`，绝不静默补 0
- SDQ：5 道反向计分题
- PHQ-A：第 9 题（自杀意念）单项直达 `CrisisLevel.ELEVATED`，不依赖总分
- 危机升级由量表自带的单项规则触发，零 LLM

### 3.3 严重度映射

| 等级 | 标签 | 颜色 |
|---|---|---|
| none | 无明显症状 | #16a34a |
| mild | 轻度 | #ca8a04 |
| moderate | 中度 | #ea580c |
| moderately_severe | 中重度 | #dc2626 |
| severe | 重度 | #b91c1c |

综合等级取所有量表的最差等级。

## 四、对话训练数据

### 4.1 数据来源与构成

合并后 **1386 条**，存储：`data/finetune/dialog_merged.jsonl`

| 来源 | 条数 | 处理脚本 | 说明 |
|---|---|---|---|
| DeepWell-Adol 清洗后 | ~600 | `convert_deepwell.py` | 剔除模板腔/封闭问句样本 |
| 云端合成 | 500 | `gen_samples_cloud.py` | qwen3.8-max 生成，100 场景 × 5 组 |
| DeepWell 改写 | ~280 | `rewrite_deepwell.py` | 保留原 human，云端 LLM 改写不合规 gpt |

### 4.2 DeepWell-Adol 数据集

- **来源**：清华深研院 EMNLP 2025，青少年积极心理对话数据集
- **仓库**：https://github.com/DeepWell-Adol/DeepWell-Adolescent
- **原始格式**：ShareGPT 多轮格式
  ```json
  {"conversations": [{"from": "human", "value": "..."}, {"from": "gpt", "value": "..."}]}
  ```
- **包含**：`Human.json`（专家撰写种子）+ `Computer.json`（机器扩增）

### 4.3 数据清洗规则

代码：`backend/scripts/finetune/gen_samples_cloud.py` L37-L63

**模板腔检测正则**（剔除）：
- `这一定让你感到.{0,6}(疲惫|沮丧|难过|痛苦|焦虑)`
- `我.{0,4}理解你的感受`
- `我能感受到你.{0,6}(的心情|的感受|的痛苦)`
- `听起来你.{0,6}(最近|这段时间).{0,4}(过得|过得很).{0,4}(不容易|辛苦)`

**闭合问句检测正则**（改写）：
- `(对吧|对吗|是不是|是吧|好吗)[？?]`
- `你觉得.{0,10}(对吧|对吗|是不是)\s*[？?]`

**开放式收尾替换池**（10 种）：
- "你能多说说这方面的情况吗？"
- "你愿意分享一下当时的感受吗？"
- "你觉得最困扰你的是哪个部分？"
- ...等

### 4.4 云端合成数据

代码：`backend/scripts/finetune/gen_samples_cloud.py`

- **模型**：qwen3.8-max（关思考链、首 token 快）
- **规模**：100 个种子场景 × 每组 5 条 = 500 条
- **并发**：8 路并发，约 100 次 API 调用
- **清洗**：复用 convert_deepwell.py 的清洗规则
- **失败重试**：单种子最大重试 2 次

### 4.5 System Prompt 注入

文件：`backend/scripts/finetune/system_prompt.txt`（318 字符）

每条训练样本均注入此 system prompt，核心约束：
1. 共情但不套话（禁止"我理解你的感受"等模板腔）
2. 简洁具体（50-100 字、不超过 3 句）
3. 开放式追问结尾（不用"对吧""好吗"等封闭问句）
4. 自然口语（不堆砌排比、不机械列举"第一第二第三"）
5. 不评判、不贴标签、不强行说教
6. 危机敏感（自伤/自杀引导 12355/120/110）

### 4.6 数据格式

最终合并后格式（ShareGPT + system 字段）：
```json
{
  "system": "你是一名青少年心理援助助手...",
  "conversations": [
    {"from": "human", "value": "..."},
    {"from": "gpt", "value": "..."}
  ]
}
```

dataset_info.json 配置：
```json
{
  "dialog_merged": {
    "file_name": "dialog_merged.jsonl",
    "formatting": "sharegpt",
    "columns": {"messages": "conversations", "system": "system"},
    "tags": {"role_tag": "from", "content_tag": "value", "user_tag": "human", "assistant_tag": "gpt"}
  }
}
```

## 五、报告训练数据

### 5.1 数据来源

- **条数**：52 条
- **存储**：`data/finetune/finetune_report.jsonl`
- **导出脚本**：`backend/scripts/export_report_finetune_data.py`

### 5.2 数据生成方式

**知识蒸馏**（teacher = 云端强模型，student = 本地 7B）：
1. 从项目历史测评数据库（SQLite）提取全部测评 session 的量表记录（总分、严重度、危机级、answers）
2. 用生产同款 `_compute_subdims()` 算子维度剖析，用生产同款 `_build_narrative()` 调云端
   **report 角色模型 deepseek-v4-flash-0731**（`LLM_MODE=cloud` 下 `role="report"` 的实际映射，不是 pro）
   生成高质量发展建议作为 teacher 输出
3. 经正则脱敏（姓名/学号模式）后，存储为 `instruction → output` 对（文件 146KB）

**导出命令**：
```powershell
docker exec -e LLM_MODE=cloud -e PYTHONUTF8=1 psycheflow-backend `
  uv run python scripts/export_report_finetune_data.py `
  --output /app/data/finetune/finetune_report.jsonl
```

### 5.3 数据格式

instruction 与生产报告生成的 user 消息格式**逐字对齐**（保证训练/推理同分布）：

```json
{
  "instruction": "本次评估结果：\n- PHQ-A 青少年抑郁筛查量表：总分 15/27，严重度「中度」\n子维度剖析：\n  · PHQ-A/认知/情感症状：4/6，等级「中度」\n  · ...\n\n请撰写发展建议。",
  "output": "## 发展建议 ...（Markdown，家庭/学校/自我调节三方面；prompt 要求 300-450 字，微调模型实测产出 644-835 字）"
}
```

dataset_info.json 配置：
```json
{
  "psycheflow_report": {
    "file_name": "finetune_report.jsonl",
    "columns": {"prompt": "instruction", "response": "output"}
  }
}
```

## 八、病例文档数据处理

代码：`backend/app/core/case_parser.py`

### 8.1 数据来源

- PDF 文件上传（仅文字版，≤10MB）
- 直接粘贴文本（≤6000 字）

### 8.2 处理流程

```
PDF bytes / 粘贴文本
    │
    ▼
extract_pdf_text() [PDF] ── pypdf 逐页 extract_text
    │
    ▼
clean_text() ── 去零宽字符/BOM、压缩空白、统一换行
    │
    ▼
truncate_case_text() ── 截断到 6000 字符
    │
    ▼
送入 LLM 结构化解读
```

### 8.3 关键参数

- `MAX_CASE_CHARS = 6000`：送入 LLM 的文本上限
- `MIN_TEXT_CHARS = 30`：判定有文本层的最低字符数（低于此值视为扫描件）

### 8.4 隐私设计

- PDF bytes 仅在内存中解析，不写磁盘
- ConversationTurn 只存文件名 + 字数，不存病例原文

## 十四、模型导出与量化

### 14.1 导出流程

```
LoRA adapter（safetensors，~155MB）
    │
    ▼ llamafactory-cli export
合并模型（HF 格式，~15GB）
    │
    ▼ convert_hf_to_gguf.py --outtype f16
F16 GGUF（15.2GB，339 个张量，~37 秒）
    │
    ▼ llama-quantize Q4_K_M
Q4_K_M GGUF（4.4GB，~4.3 分钟）
```

### 14.2 量化策略

- **token_embd / output**：q6_K（保精度）
- **attn / ffn 主体**：q4_K_M
- **压缩率**：f16 14526 MiB (16.00 BPW) → Q4_K_M 4460 MiB (4.91 BPW)

### 14.3 为什么分两步导出

`convert_hf_to_gguf.py` 的 `--outtype` 仅支持 f32/f16/bf16/q8_0/auto，不直接支持 q4_k_m。所以：
1. 先转 f16
2. 再用现场编译的 `llama-quantize` 量化到 Q4_K_M

### 14.4 本地导入

```powershell
powershell -ExecutionPolicy Bypass -File backend\scripts\finetune\import_gguf.ps1
```

导入后 `ollama list` 应看到：
- `qwen2.5:dialog-lora`
- `qwen2.5:report-lora`

## 十六、数据与模型 Q&A

### Q1：对话训练数据来自哪里？

三个来源合并共 1386 条：DeepWell-Adol 公开数据集清洗后约 600 条、云端 qwen3.8-max 合成 500 条、DeepWell 原样本云端改写约 280 条。每条注入 318 字符的 system prompt 约束行为。

### Q2：为什么用 QLoRA 而不是全量微调？

7B 模型全量微调需要大量显存（至少 40GB+），QLoRA 用 4bit 量化基座 + LoRA 适配器，24GB 显存即可训练。可训练参数仅 0.5273%，训练成本极低（约 4 元），效果接近全量微调。

### Q3：LoRA 的 rank 和 alpha 怎么选的？

dialog 用 rank=32/alpha=64，因为数据量大（1386 条）且任务是开放式对话，需要更大容量学多样表达。report 用 rank=16/alpha=32，因为数据量小（52 条），过大容易过拟合。alpha 通常设为 rank 的 2 倍。

### Q4：report 训练数据只有 52 条，会不会过拟合？

数据量小是事实，所以用了 rank=16（比 dialog 小）、epochs=3（比 dialog 少）。report 任务是结构化长文生成，loss 高（2.28）属正常。实际效果通过 eval_report 验证：5/5 场景全通过，发展建议 644-835 字结构完整。

### Q5：训练数据怎么清洗的？

用正则检测模板腔（"我理解你的感受""这一定让你感到..."等）和闭合问句（"对吧""是不是""好吗"等）。模板腔样本直接剔除，闭合问句样本用云端 LLM 改写为开放式收尾。

### Q6：为什么 triage 不用微调模型？

危机红线不能受微调影响。triage 用 qwen2.5:7b 基座保证意图分类的确定性，特别是危机类 100% 命中靠硬编码词表，不依赖模型。实测 0.5b 模型准确率仅 48.8%，所以 triage 切回 7b 基座。

### Q7：量化为什么选 Q4_K_M？

Q4_K_M 在 4bit 量化中质量较好，token_embd 和 output 用 q6_K 保精度，attn/ffn 主体用 q4_K_M。4.4GB 大小可在 RTX 4060 8GB 显存运行，是质量和显存的平衡点。

### Q8：知识库数据怎么来的？

基础科普层 10 个 .txt 是内部编写基于临床心理学常识整理，技术方法层 8 个 .md 参考 CBT/DBT 等公开心理学资料。每个文件标注来源和适用场景标签。改完必须重建 RAG 索引。

### Q9：量表数据来自哪里？

四套量表都是国际通用量表的本土化版本：PHQ-A（基于 PHQ-9）、SCARED（Birmaher 编制）、SDQ（Goodman 编制）、MHT（周步成等修订）。计分规则严格按照量表手册实现，用 Python 规则不用 LLM。

### Q10：报告训练数据怎么生成的？

知识蒸馏：从项目历史测评数据库提取 52 条记录，用云端 **report 角色模型 deepseek-v4-flash-0731**（导出时 LLM_MODE=cloud）生成高质量发展建议作为 teacher 输出，instruction 与生产输入格式逐字对齐，脱敏后存储为 instruction→output 对。这样小数据也能学到高质量生成模式。

## 十七、答辩九问精答（2026-09-09 实测核对版）

### Q1：知识库数据有多少？

**结论：截至 2026-09-10（18.1 第一轮扩充后），实测 32 个文件 = 19 个 .txt + 13 个 .md**（答辩当天 2026-09-09 为 19 个 = 10 .txt + 9 .md；更早文档曾误记为 8 个 .md）。

- 19 个 .txt 科普层：01–10 基础科普（情绪/共情/危机/放松/睡眠/焦虑/抑郁/欺凌/亲子/学业）+ 11–19 缺口主题（网瘾/NSSI/创伤/ADHD/进食/哀伤/青春期情感/考试焦虑/时间管理，均为 18.1 新增）
- 13 个 .md 方法层：原 9 个（cbt_intro、cbt_techniques、ccmd3_summary、dbt_skills、nhc_hotline_guide、psych_case_glossary、relaxation_exercises、sadpersons_scale、safety_plan_template）+ 18.1 新增 4 个具名权威摘要（cbti_manual、nvc_parent_scripts、school_crisis_referral、mood_disorder_guidelines）
- **文件数 ≠ 数据量**：32 个文件经结构感知切片（chunk_text，40-400 字/片、Markdown 章节前缀、句子边界切分）后 = **327 个检索切片、共 44,485 字**（2026-09-10 用 load_corpus() 实测）。RAG 的检索单位是切片不是文件，切片最多的是 relaxation_exercises.md（18 片）、dbt_skills.md（17 片）。
- **检索质量有量化护栏**：65 条 query→期望文件评测集，recall@3=100%、32/32 文件覆盖（eval_rag.py，详见 18.1.6）。

> 答辩话术：「知识库目前是 32 份文档、327 个检索切片、约 4.4 万字，其中 13 份是具名权威
> 来源摘要、19 份是标注「内部编写、科普用途」的青少年主题科普。我们没有堆文档数量，
> 而是把工程重点放在切片质量和检索护栏上——每片带章节前缀、有适用场景标签、以完整
> 句子收尾，检索的最小单位是带上下文的切片；每次扩充后跑 65 条评测集，recall@3 100%
> 才放行。」

### Q2：报告训练数据是什么？

**结论：52 条 instruction→output 蒸馏样本对**（`data/finetune/finetune_report.jsonl`，146KB）。

- **instruction**：从 SQLite 历史测评库导出的量表总分/严重度 + `_compute_subdims()` 算出的子维度剖析，格式与生产环境 `_build_narrative()` 的输入**逐字对齐**（训练/推理同分布）
- **output**：导出时以 `LLM_MODE=cloud` 调云端 **report 角色模型 deepseek-v4-flash-0731**（注意：是 flash 不是 pro）生成的发展建议，经正则脱敏（姓名/学号模式替换）
- 方法学名称：**知识蒸馏**——云端强模型当 teacher 产出标注，本地 7B 当 student 学习
- 为什么 52 条够用：报告输入空间是结构化分数组合（4 量表 × 5 级严重度 × 固定子维度），52 条覆盖主要组合；防过拟合靠 rank=16、epochs=3、lr=5e-5；效果由 eval_report 76 项断言兜底验证

### Q3：向量阈值是 0.75 还是 0.6？

**结论：阈值已改为按嵌入模型自适应——云端 text-embedding-v3 用 0.75，本地 bge-m3 用 0.95**（[service.py](file:///e:/Trae/PsycheFlow/backend/app/rag/service.py) 常量 `VEC_THRESHOLD_CLOUD=0.75` / `VEC_THRESHOLD_LOCAL=0.95`，`search(threshold=None)` 时 `_default_threshold()` 按 `llm.is_local` 取值）。四个要点：

1. **这是 L2 距离阈值，不是相似度**：距离越小越相关，`distance > 阈值` 才被过滤。所以 0.60→0.75 是**放宽**召回，不是收紧。
2. **为什么本地要 0.95**：bge-m3 输出已归一化（范数 1.0），L2 距离尺度与云端 v3 完全不同——相关片段实测 0.77–0.91、无关片段 ≥1.10；沿用云端 0.75 会把本地模式几乎全部片段误杀。**换嵌入模型必须重新实测距离分布再定阈值**。
3. **演变原因**：0.60 过严，把「腹式呼吸」这类无"焦虑"关键词但语义高度相关的做法片段误杀，导致"求方法"类问题召回不到直接做法；放宽后由来源去重保证多样性。
4. **混合检索的其他常数**（同文件）：BM25 独有命中给**虚拟距离 = 阈值−0.03**（相对值，随模式自适应；早期固定 0.72/0.55 已废弃，且不再做关键词加权——加权曾让 BM25 片段反超真实向量命中）；BM25 入选门槛 score ≥ 0.7×局内最高分；向量+BM25 双重命中距离减 0.03；**BM25 候选必须透传 tags**（否则非危机 query 经 BM25 路径漏入「危机」片段，有单测守护）。排序为**向量距离主排序 + BM25 补充召回**；非危机查询额外排除带「危机」标签的片段。

### Q4：语言有没有本地化？

分两个层面回答，不要混为一谈：

1. **界面与交互语言：纯中文，刻意不做多语言（i18n）**。目标用户是中国中小学生和教师：四套量表都是中文修订版（MHT 为周步成等修订）、危机干预热线是 12355、合规话术基于国内场景。前端工程中不存在 i18n/locale 框架（全仓 grep 无匹配）。报告中少量英文（如 "Mentally Healthy"）仅为版式装饰。
2. **语言能力的本地（离线）化：local 模式全链路中文模型本地运行**——LLM 用 Qwen2.5-7B（中文同尺寸最强开源模型之一）、向量用 bge-m3（中文检索 SOTA，1024 维）、语音 ASR 用 faster-whisper、TTS 用 sherpa-onnx VITS（接 rule_fsts 修正"12355"数字读法），数据不出本机、可离线。

> 边界：local 模式下语音 ASR/TTS 的云端选项仍保留（qwen-audio），通过 voice_mode 切换。

### Q5：模型选型是怎么考虑的？

四条决策依据：

1. **中文能力优先**：Qwen2.5 系列中文语料充分、Apache-2.0 许可可商用；bge-m3 是中文向量检索的开源 SOTA；
2. **显存硬约束**：本地目标硬件 8GB（RTX 4060 Laptop）→ 7B Q4_K_M（4.7GB）+ bge-m3（1.2GB）= 5.9GB 可常驻；14B Q4 约 9GB 装不下；qwen2.5:0.5b 做 triage 实测准确率仅 48.8%，被证伪淘汰，triage 回到 7B；
3. **云端按角色分工**：intake 用 MoE 小模型做结构化提取；triage/dialog_stream 用可关思考链的模型（首 token 0.38s/0.58s）保证响应速度；dialog 用 deepseek-v4-pro 保共情质量；report 用 flash 控成本；embedding 用专用 text-embedding-v3；
4. **生态与工程闭环**：Ollama 提供 OpenAI 兼容接口 + GGUF 量化 + 整机共享容器；LLaMA-Factory 覆盖 QLoRA 训练→合并→GGUF 量化全链路。

> 核心原则（安全设计）：**安全关键路径不用模型**——危机词表检测、量表计分、报告危机红框全部硬编码规则，模型只负责自然语言生成。

### Q6：报告是怎么生成的？

四段式流水线（[reports/service.py](file:///e:/Trae/PsycheFlow/backend/app/reports/service.py#L760) `generate_report_pdf`）：

1. **规则计分（零 LLM）**：量表引擎算总分/严重度/危机级（PHQ-A 第 9 题自杀意念单项直达危机升级）；`_compute_subdims()` 按量表手册算子维度（PHQ-A 4 维、SCARED 5 维、SDQ 5 维含反向计分、MHT 8 维）；
2. **LLM 写发展建议**：总分+子维度剖析喂给 report 角色，system prompt 要求 300-450 字、家庭/学校/自我调节三方面可执行建议、中重度必须明确建议专业干预；max_tokens=4000（容纳思考链）；**空回复/异常时走硬编码兜底建议**（保证非空）；
3. **模板渲染**：Jinja2 渲染 report.html，结构对齐 MHT 纸质报告 6 大章节（工具介绍→解读注意事项→人员信息表→测评结果：综合等级横幅+SVG 雷达图+总览表+因子剖析表→因子详解卡→发展建议）；雷达图是纯几何计算的 SVG，不依赖绘图库；
4. **WeasyPrint 出 PDF**，同步写审计（audit_logs 表 + JSON 文件双写）。

**危机红框（crisis_message + 12355 热线）是硬编码插入**，位于等级横幅与信息表之间，零 LLM——即使模型试图淡化风险，红框不可绕过。实测：5 场景 76 项结构断言全通过，发展建议 644-835 字，PDF 137-169KB。

### Q8：不考虑训练成本，只考虑我的电脑（RTX 4060 Laptop 8GB），跑微调模型效果最好的办法是什么？

**现状瓶颈**：三个 7B 模型（基座 4.7 + dialog-lora 4.7 + report-lora 4.7GB）+ bge-m3 1.2GB ≈ 14.6GB，
8GB 显存无法同时常驻，Ollama 只能换入换出，角色切换冷加载约 40 秒。

**最优方案：合并角色 → 单模型常驻，把省下的显存换成更高量化精度**：

| 步骤 | 做法 | 显存账 |
|---|---|---|
| 1 | dialog 1386 条 + report 52 条合并训练**一个统一 LoRA**（靠 system prompt 区分对话/报告任务），导出一个统一 7B GGUF | 4.7GB（Q4_K_M） |
| 2 | triage/intake 也复用该模型：意图分类本就是基座能力，且 triage 前置已有 detect_crisis / detect_greeting / detect_method_question 三层零 LLM 规则拦掉大部分流量；换型后跑 eval_triage 验证 ≥95% 即验收 | 0 额外 |
| 3 | bge-m3 改为 **CPU 运行**：每轮 RAG 仅 1 次 query embedding，CPU 延迟约 200ms，可换出 1.2GB 显存 | -1.2GB |
| 4 | 腾出的显存把统一模型升到 **Q5_K_M（约 5.4GB）**，推理质量再提一档 | 5.4GB |
| 合计 | Q5 统一模型 5.4GB + 8192 上下文 KV cache 约 1.5GB ≈ 7GB，8GB 舒适常驻、**零模型切换** | ~7GB |

- **不重训的立即优化**（今天可做）：bge-m3 上 CPU + `OLLAMA_KEEP_ALIVE=-1` 保持单模型常驻 + 按角色设 num_ctx（triage 4096 / report 8192）控制 KV cache。
- **不要做的**：14B（Q4 约 9GB 装不下，部分层 offload 到内存速度腰斩）；指望 Ollama 多 LoRA 同时热驻（单进程不支持多 adapter 常驻）。

### Q9：补充丰富很多数据之后，SQLite 需要替换吗？

**结论：不需要。可预见的校园规模下 SQLite 完全够用。** 先分清"补数据"补到哪里：

- 知识库扩充 → 落文件 + Chroma 向量库，**不进 SQLite**；
- 训练数据扩充 → JSONL 文件，**不进 SQLite**；
- 只有业务数据（用户/会话/对话轮次/测评记录/批次/审计）进 SQLite，而它增长极慢。

**容量实测与测算**：

- 当前库 **1.49MB**（2026-09-09 实测），7 张表；
- 千人学校每年：约 2000 条测评（answers JSON ≈1KB/条）+ 2 万轮对话（≈0.5KB/轮）≈ **12MB/年**；
- 万人规模 × 10 年 ≈ **120MB**；SQLite 官方能力上限到 TB 级，读多写少短事务场景 10GB 内无压力。

**真正的限制与对策**：

- SQLite 的瓶颈是多写者并发锁；本系统写操作都是单条 INSERT 短事务，建议显式开启 **WAL 模式**
  （`PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;`，读写不互斥）——这是当前唯一建议补做的小优化；
- 合规能力已具备：文件权限 0600、备份 AES-256-CBC 加密（backup_db.py）、审计双写；
- **未来迁移触发点**：多校多服务器水平部署、写 QPS 达数百成为瓶颈、或需要对对话内容做 DB 级全文检索
  → 再上 PostgreSQL。因数据访问全部走 SQLAlchemy ORM，迁移主要改连接串和 JSON 类型适配，业务代码基本不动。

### 18.3 本地 4060 8GB 效果最优模型方案（训练成本不计版）

> 约束：云服务器训练成本不考虑；只看最终成品在 RTX 4060 Laptop 8GB 上的运行效果。

#### 18.3.1 基座选型：Qwen3-8B-Instruct

| 方案 | 权重占用 | KV cache(8k) | 8GB 可行性 | 结论 |
|---|---|---|---|---|
| **Qwen3-8B Q5_K_M（首选）** | ~5.9GB 文件 / 加载 ~5.5GB | 36层×8KV头 ≈ 1.2GB（KV q8_0 可减半到 0.6GB） | 5.5+1.0+0.7 ≈ **7.2–7.5GB 可常驻** ✅ | 综合能力对标 Qwen2.5-14B 档，显著强于 2.5-7B |

**Qwen3-8B 两个硬注意事项**：

1. **必须全程关闭思考链**：训练时用 LLaMA-Factory qwen3 模板关 thinking（样本不含思考过程）；Ollama Modelfile/API 固定 `/no_think`（think=false），否则思考链拖垮延迟、可能外泄 `<think>` 内容；验收专门检查输出无思考残留；
2. 训练/导出/评测链路按 qwen3 模板跑通（GGUF 转换 llama.cpp 已支持 Qwen3），四套评测脚本重设基线。**若关思考后实测不稳定，保底回退 Qwen2.5-7B Q6_K**（流水线零改动）。

#### 18.3.2 训练方法：全参 SFT + DPO 两步走

训练在云端做（8GB 卡不做 7B+ 训练；推理侧才是 4060）。

1. **数据阶段**：按 18.2 产出 ~6000 条三任务混合 SFT 数据（强 teacher + best-of-4 + 判官过滤）；
2. **第一步：全参数 SFT**。租 **A100 80GB**（或 H200；4090 24GB 做不了全参 8B），bf16 + 8-bit Adam：
   - lr 1e-5、epochs 3、effective batch 32、cosine、warmup 0.03、cutoff_len 2048；
   - 全参 FT 需约 60–80GB 显存；LoRA（r64/alpha128）在 4090 上是可接受替代，但成本不计时全参是质量上限；
3. **第二步：DPO 偏好优化（反模板针对性一击）**：
   - chosen = 过全部安全规则的回复；rejected = 模板腔开头/闭合问句/幻觉归因/复读上轮的回复——**280 条被改写的模板腔数据是天然 rejected 池**，再用模型采样补充；
   - ~2000 对，lr 5e-6，1–2 epoch；
   - 原理：SFT 教"怎么说"，DPO 直接教"哪种说法更差"，对反模板这类风格目标比继续堆 SFT 有效。

#### 18.3.3 导出与部署配方（8GB 舒适常驻）

1. 全参 FT 无合并步骤，直接 f16 GGUF → llama-quantize 出 **Q5_K_M**（~5.9GB，两步导出法同现有 cloud_train.sh）；
2. 导入 Ollama，Modelfile：`num_ctx 8192`（紧张则 6144，dialog/report 实测 token 峰值 ~5k）、固定关思考、`OLLAMA_KEEP_ALIVE=-1`；
3. ollama 容器加 **`OLLAMA_KV_CACHE_TYPE=q8_0`**：KV cache 1.2GB→0.6GB（精度损失对生成质量基本无感）；
4. **bge-m3 挪 CPU**：另建 `bge-m3-cpu` tag（`PARAMETER num_gpu 0`），`.env` 设 `LOCAL_EMBED_MODEL=bge-m3-cpu`——权重没变，**RAG 索引不用重建**；每轮仅 1 次 query embedding，CPU 延迟约 200ms；
5. **ASR 固定 CPU int8**：whisper-medium 懒加载会抢 ~1.5GB 显存，CPU int8 转写短语音 2–5s 可接受，显存全留给主模型（TTS 本就在 CPU）；
6. `.env`：`LOCAL_MODEL=qwen3:unified-q5`，`LOCAL_MODEL_DIALOG/REPORT/TRIAGE` 全留空（代码留空即回退 LOCAL_MODEL，见 llm.py model_for）；
7. `docker compose up -d backend` 重建容器（改 .env 必须 up 不能 restart）。

**显存账**：Q5 权重 ~5.5GB + KV cache(q8_0) ~0.6GB + 运行时 buffer ~0.7GB ≈ **6.8–7.0GB，余 ~1GB，单模型零切换常驻**；bge-m3/ASR/TTS 均不占显存。
