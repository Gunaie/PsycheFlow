## 一、项目定位与核心价值

### 1.1 一句话定位

PsycheFlow 是面向中小学生的校园心理筛查辅助系统，集成标准化心理测评、开放式 AI 陪伴对话、智能报告生成三大能力，支持学生匿名作答与教师批量筛查两种场景。

**非医疗器械，不替代专业诊疗。**

### 1.2 解决的核心问题

| 痛点 | 本系统方案 |
|---|---|
| 校园心理筛查靠人工，效率低 | 4 套标准化量表自动计分，批量筛查 |
| 学生不愿面对面倾诉 | 匿名 AI 对话，降低心理门槛 |
| 危机识别依赖经验 | 硬编码关键词前置扫描，零 LLM 秒级响应 |
| 报告撰写耗时 | LLM 生成发展建议 + 规则计分，对齐 MHT 结构 |
| 数据隐私顾虑 | 本地 Ollama 私有化部署，数据不出本机 |

### 1.3 核心设计原则

1. **安全前置**：危机检测必须在所有 LLM 调用之前执行，硬编码不依赖模型概率
2. **确定性优先**：量表计分用规则不用 LLM，保证可复现
3. **分级降级**：云端 API → 本地 Ollama → 节点硬编码话术三级兜底
4. **隐私合规**：知情同意链、匿名作答、SQLite 0600、备份 AES 加密

## 三、LangGraph 四智能体编排详解

### 3.1 拓扑结构

代码：[graph.py](../backend/app/agents/graph.py)

```
START → triage
         │
         ├── is_crisis=true ──────→ escalation → END
         │
         ├── final_reply 非空 ─────→ END（寒暄直达）
         │
         └── 其余 ──→ assessment → intervention → END
```

**关键代码**（graph.py L19-L55）：
- `route_after_triage` 条件边函数：判断 crisis / final_reply / assessment 三条路
- `build_graph()` 构建 StateGraph 并编译为单例 `graph`

**为什么用 LangGraph 不用手写 if-else**：
对话链是有状态（AgentState 在节点间传递）、有条件分支的 DAG。LangGraph 的 `StateGraph` + `add_conditional_edges` 天然表达这种结构，状态流转清晰。新增节点只需 `add_node` + `add_edge`，不动已有逻辑。

### 3.2 Triage 分诊节点（最核心）

代码：[triage.py](../backend/app/agents/nodes/triage.py)

**全规则路由**（2026-09-30 起零 LLM，按执行顺序）：

| 层级 | 机制 | 实现 | 命中后行为 |
|---|---|---|---|
| 第 1 层 | 危机硬编码扫描 | `detect_crisis()` 关键词子串匹配（`CRISIS_KEYWORDS`） | `is_crisis=true`，零 LLM 直达 escalation |
| 第 2 层 | 寒暄硬编码识别 | `detect_greeting()` 白名单正则（≤30 字纯寒暄短句） | 走 `_greeting_fast_path` 快速通道，静态硬编码话术产出 `final_reply` |
| 第 3 层 | 咨询规则 | `detect_service_question()` / `detect_method_question()` / `detect_knowledge_question()` | 设 `triage_intent=咨询`，进入 assessment → intervention |
| 第 4 层 | 求助渠道识别 | `detect_help_channel()` | 硬编码推荐学校心理中心/精神卫生中心/线上平台，产出 `final_reply` |
| 第 5 层 | 求助祈使识别 | `detect_help_plea()` | 设 `triage_intent=求助`，进入 assessment → intervention（跳过 RAG） |
| 兜底 | 默认倾诉 | 以上均未命中 | 设 `triage_intent=倾诉`，进入 assessment → intervention |

**关键规则**（全零 LLM）：
- **危机词表**：`safety.py` 14 个关键词，子串匹配，命中即短路，不依赖模型概率判断
- **方法问句正则**：`(怎么/如何/怎样)…(缓解/改善/克服/应对/调节/调整/治疗/解决/控制/沟通/专注/自律/帮)`、`怎么办`、`有什么办法/方法`，≤35 字守卫 → 判为「咨询」
- **服务问句**：询问保密/能力/政策 → 判为「咨询」
- **求助祈使**：「帮帮我/救救我/谁来帮帮」等直接求助 → 判为「求助」

**寒暄快速通道**（triage.py L214-L241）：
- 静态硬编码话术两套（身份询问/纯打招呼），0.0s 响应
- 话术按 `check_reply_quality` 约束预校验（≤120 字、无闭合问句），由 test_agents_triage.py 守护，直通产出 `final_reply` 不再过质检

> 注：原 triage-lora（1010 条训练）已停用，模型资产保留作历史回退。

### 3.3 Assessment 测评节点

职责：查询当前会话是否有未完成的测评，将测评结果（分数、严重度、危机等级）注入 state，供 intervention 节点在回复中参考。

### 3.4 Intervention 干预节点

代码：[intervention.py](../backend/app/agents/nodes/intervention.py)

**核心流程**：
1. `build_intervention_messages()` 拼接 prompt
2. `provider.chat(role="dialog", temp=0.6)` 生成共情回复
3. `check_reply_quality()` 质检，不合格走**三级重试阶梯**（见 §6.2）
4. 空回复/异常 → `FALLBACK_REPLY`（含 12355 热线）

**三级质检重试阶梯**（2026-10-01 升级）：
| 级别 | 模式 | 做法 | 温度 |
|---|---|---|---|
| ① | hint | `build_retry_hint()` 按违规点动态生成禁令（点名复读原句截 60 字 + 上轮做法类别中文标签） | 0.6 |
| ② | rag_refresh | `_refresh_rag_sources()` 检索 top_k=6 排除已引用 chunk，取新鲜 3 条重拼 prompt | 0.7 |
| ③ | context_trim | history 剔除 assistant 回复（保留 user 保连贯）+ 换片重拼 | 0.7 |

不变式：每次重试重新质检，全失败保留首次回复，`decision.llm.retry_modes` 留痕。

**RAG 检索策略**（intervention.py L304-L327）：
- `triage_intent` 为「寒暄」或「求助」时**跳过 RAG**（问候和测评引导与心理知识无关）
- 其余意图调用 `rag_service.search(message, top_k=3)`
- 每段知识片段截断到 350 字，最多取 3 段

**历史裁剪**：只保留最近 20 条（10 轮）user/assistant 消息，防 token 膨胀

### 3.5 Escalation 危机升级节点

职责：命中危机时，输出硬编码的 `crisis_message()`（含 12355 热线），同时：
- 写 `crisis_*.json` 文件到 logs 目录
- 写 `AuditLog` 到数据库（双写留痕）
- `ConversationTurn.crisis_hit = true`

## 四、危机处理机制

### 4.1 设计原则

**危机检测必须零 LLM、硬编码、前置执行。**

原因：心理危机是高风险场景，LLM 是概率性判断，可能漏判或延迟，漏判代价不可接受。硬编码关键词扫描是确定性的，秒级响应。

### 4.2 关键词词表

代码：[safety.py](../backend/app/core/safety.py) L9-L13

```python
CRISIS_KEYWORDS = [
    "自杀", "自残", "自伤", "不想活", "想死", "结束生命",
    "割腕", "跳楼", "了结自己", "活不下去", "轻生",
    "活够了", "没意义了", "不想存在",
]
```

匹配方式：小写子串匹配，命中按出现顺序去重收集。

### 4.3 危机响应话术

代码：safety.py L40-L48

```
"我听到你正在承受很大的痛苦，你的感受很重要，你不是一个人。
作为校园心理陪伴助手，我不能替代专业帮助——
请立即联系你信任的老师、家长，或拨打青少年心理援助热线 12355，
专业人员会陪着你一起面对。"
```

特点：温暖但坚定，不替代专业帮助，提供 12355 热线。

### 4.4 危机留痕双写

| 存储位置 | 内容 | 用途 |
|---|---|---|
| `logs/crisis_*.json` | 完整危机事件快照 | 文件级审计 |
| `AuditLog` 表（DB） | event_type=crisis + payload | 可查询/聚合/合规导出 |
| `ConversationTurn.crisis_hit` | 布尔标记 | 对话流中标识危机轮次 |

### 4.5 报告中的危机兜底

代码：[reports/service.py](../backend/app/reports/service.py) L8-L10

危机升级情形下，在报告"综合等级横幅"与"人员信息表"之间硬编码红色危机框，零 LLM。即便 LLM 建议软化，硬框不可绕过。

## 五、RAG 知识库系统

### 5.1 知识库构成

目录：`data/knowledge/`

| 类型 | 数量 | 说明 |
|---|---|---|
| 基础科普 .txt | 19 个 | 01-10 基础科普（情绪识别/焦虑/抑郁/睡眠/放松/学业压力/社交恐惧/网瘾/自伤/创伤）+ 11-19 缺口主题（ADHD/进食障碍/哀伤/青春期情感/考试焦虑/时间管理） |
| 权威方法 .md | 13 个 | cbt_intro/dbt_skills/relaxation_exercises/cbti_manual/nvc_parent_scripts/school_crisis_referral/mood_disorder_guidelines 等具名权威摘要 |

**规模**：32 文件 / 327 片 / 44,485 字（2026-09-10 实测）。

每个文件头部有两行元数据：
```
来源：内部编写，基于XX整理（科普用途，不构成诊疗建议）
适用场景：焦虑,放松
```

### 5.2 结构感知切片

代码：[service.py](../backend/app/rag/service.py) L70-L107

**切片参数**：
- `MAX_CHUNK_CHARS = 400`：单片正文上限，超长按句子边界二次切分
- `MIN_CHUNK_CHARS = 40`：缓冲下限，过短段落并入相邻段
- `MAX_SECTION_PREFIX = 40`：章节前缀截断长度

**切片规则**：
1. 按空行分段
2. Markdown 标题行（#/##/###）作为"章节"，给后续段落加 `【章节】` 前缀，不单独成片
3. 过短段落（<10 字）丢弃
4. 超长段落按句子边界（。！？；）二次切分，保证每片"有头有尾"

**为什么不用固定长度切片**：固定长度切片会把完整句子切断，产生"没头没尾"的碎片，向量检索时语义不完整。结构感知切片保证每片都有章节标题前缀和完整句子收尾。

### 5.3 元数据解析

代码：service.py L110-L129

`parse_metadata()` 函数：
- 剥离 `来源：` 和 `适用场景：` 行
- 标签用逗号分隔，存入 Chroma metadata
- 用于检索时的场景过滤

### 5.4 混合检索策略

代码：service.py L239-L407

**检索流程**：
1. **向量检索**：嵌入模型向量化 query，Chroma 查询 top_k×3
2. **BM25 检索**：jieba 分词，`BM25Okapi` 关键词匹配
3. **融合排序**：
   - 以向量 L2 距离为主排序信号
   - BM25 独有命中（向量未召回）给虚拟距离 = 阈值 − 0.03（相对值）
   - 双重印证（向量+BM25 都命中）距离减 0.03
   - 关键词命中（压力/失眠/焦虑等）距离减 0.05
4. **过滤+去重**：
   - 距离超过阈值丢弃
   - 非危机查询排除带 `危机` 标签的片段
   - 同一来源只保留一篇

**阈值自适应**（2026-09-09 定版）：
- 云端 text-embedding-v3：0.75
- 本地 bge-m3：0.95（bge-m3 输出归一化向量，L2 距离分布不同，相关片段 0.77-0.91，无关 ≥1.10）
- 切换 embedding 模型后必须实测距离分布再定阈值

**为什么不用 RRF 排名融合**：RRF 让 BM25 关键词命中权重过大，「焦虑怎么缓解」中仅含"缓解"关键词的科普片段会挤掉含具体做法、向量距离更近的片段。向量语义相似度比关键词命中更能反映相关性。

### 5.5 检索埋点与护栏

**检索埋点**（2026-09-10 落地）：
- 每次 `rag_service.search()` 追加一行 JSON 到 `logs/rag_search_YYYYMMDD.jsonl`
- 记录 query/意图/阈值/top1 距离/是否放行/top3 文件tags，不记用户标识
- 周度聚类：`analyze_rag_gaps.py` 统计弱命中，同主题簇单周 ≥5 次立项补知识库

**评测护栏**：
- `eval_rag.py`：65 条 query→expect 文件，recall@3 应 100%，32/32 文件覆盖
- 知识库每次扩充/改检索逻辑后必须 `build` 索引 + 跑 eval_rag，recall@3 下降即阻断
- 2026-09-26 基线：hit@1 76.9%，recall@3 100%，MRR 0.874

**实测数据**（2026-10-01）：433 条真实流量（全部 intervention 调用），信号① 0 条零命中，信号② 1 条放行但不可用，信号③ 0 条 eval miss。

### 5.6 索引重建

改完知识库必须执行 `POST /api/rag/build`：
- `load_corpus()` 读取所有 .txt/.md，解析标签，切片
- `reset_namespace()` 清空旧集合（切片规则变更后 chunk ID 变化，旧片残留会污染检索）
- `provider.embed()` 批量向量化（cloud 每批 10 条，local 每批 8 条）
- 写入 Chroma，metadata 含 source + tags
- 重置 BM25 索引

## 六、反模板对话质量控制

### 6.1 问题背景

本地 LoRA 微调模型（7B Q4 量化）有两个高频坏习惯：
1. **闭合问句**：用「对吧」「是不是」「好吗」收尾，压制对话开放性
2. **复读上轮**：复读用户上一轮的问句或自己上一轮的建议

### 6.2 四层控制体系

#### 第一层：Prompt 硬规则

代码：[prompts.py](../backend/app/agents/prompts.py) L45-L60

`INTERVENTION_USER_TEMPLATE` 第 5 条明确禁止：
- 闭合问句：对吧/对吗/是不是/是吧/好吗/对不对/好不好/会不会/有没有/能不能/可以吗 + 句末「吗？」「吧？」
- 整轮最多一个问题
- 不得重复上轮建议与问句
- 同一种做法换说法也算重复（如「腹式呼吸」和「手放肚子上感受呼吸起伏」是同一种）
- 「你说过…」只能指历史中真实出现的内容
- 做法多样性：求做法问题须 ≥2 种不同类别，且与上轮做法不重复

#### 第二层：回复质检函数

代码：[intervention.py](../backend/app/agents/nodes/intervention.py) L201-L281

`check_reply_quality(reply, history, min_method_categories)` 检查项：

| 检查项 | 规则 | 不合格处理 |
|---|---|---|
| 闭合问句 | 正则匹配违禁词 + 句末「吗？」「吧？」 | 走三级重试 |
| 问题数量 | 问号超过 1 个 | 走三级重试 |
| 长度下限 | 干预回复 < 50 字 | 走三级重试 |
| 长度上限 | 超过 120 字 | 走三级重试 |
| 逐字重复 | 与历史某条 assistant 回复有 ≥12 字公共片段（呼吸 4吸6呼 公式豁免） | 走三级重试 |
| 幻觉归因 | 「你说过X」中 X 不在用户历史中 | 走三级重试 |
| 同类做法重复 | 本轮做法类别与上轮有交集 | 走三级重试 |
| 做法多样性 | 求做法问题须 ≥2 种不同类别 | 走三级重试 |

**做法类别映射**（intervention.py L51-L60）：
- breathing：呼吸/肚子/吸气/呼气/腹式/喘气/气息
- journaling：写/本子/日记/记下来/纸笔/写下来
- muscle_relax：肌肉/紧张再放松/渐进式/握拳/握紧/绷紧
- mindfulness：正念/冥想/观察/当下/感受身体
- exercise：运动/跑步/散步/拉伸/走动
- planning：任务拆解/拆成/清单/列出来/计划表（2026-10-01 新增，对齐 prompt 骨架）

#### 第三层：三级质检重试阶梯

代码：intervention.py L498-L605（非流式 `intervention_node`）与 L385-L495（流式 `stream_intervention`）

质检不合格时走**三级重试阶梯**（流式/非流式同源）：

| 级别 | 模式 | 做法 | 温度 |
|---|---|---|---|
| ① | hint | `build_retry_hint()` 按违规点动态生成禁令：`_find_verbatim_overlap()` 点名复读原句截 60 字 + 上轮做法类别中文标签 | 0.6 |
| ② | rag_refresh | `_refresh_rag_sources()` 检索 top_k=6 排除已引用 chunk，取新鲜 3 条重拼 prompt | 0.7 |
| ③ | context_trim | history 剔除 assistant 回复（保留 user 保连贯）+ 换片重拼 | 0.7 |

不变式：每次重试重新质检，合格才采用；重试异常/空/仍不合格 → 保留首次回复；②③ 共享 alt_chunks（rag.search 最多 2 次）；`decision.llm.retry_modes` 留痕。

**三级阶梯经验**：
- 评测暴露 RETRY_HINT 自身是复读种子（示例「把担心的事写在纸上」被 7B 照抄补完库存句）→ 修复为抽象类别表述
- 呼吸参数公式（4吸6呼）与复读判定的语义冲突 → 检测前剥离公式（哨兵占位），公式外真实复读仍判不合格
- 三级阶梯把多轮评测同类做法重复类失败清零

**流式模式**：先缓冲完整生成再质检，通过后按字符匀速补推（0.012 秒/字符，恢复打字机效果）

### 7.3 LLM 三级降级链

代码：[llm.py](../backend/app/core/llm.py)

**非流式 `chat()`**（llm.py L178-L248）：
- cloud 模式：百炼异常或空回复 → 若启用 Ollama 则转本地 → 仍失败返回 ""（节点级硬编码兜底）
- local 模式：直走 Ollama，异常/空回复返回 ""（不回退云端，保证数据不出本机）

**流式 `stream()`**（llm.py L249-L293）：
- cloud 流起始即失败（未 yield 任何 token）→ 转 Ollama 流式
- 已部分输出则不切换（避免拼接错乱）
- local 模式直走 Ollama 流式

**关键细节**：
- deepseek-v4 系列有 `reasoning_content` 思考链字段，`max_tokens` 须足够容纳 reasoning + content（否则 content 为空，finish_reason=length）
- triage/dialog_stream 两角色通过 `enable_thinking=False` 关闭思考链，保证首 token 速度
- 流式只 yield `content`（最终回复），思考链不推给用户

### 10.2 SSE 事件格式

代码：chat.py L187-L377（`chat_stream` 内事件推送）

```
event: <type>
data: <json>

```

| 事件类型 | 内容 | 时机 |
|---|---|---|
| agent | {agent, agent_trace} | 节点切换 |
| sources | {sources} | intervention 前推 RAG 卡片 |
| token | {token} | 流式 token（非危机路径） |
| crisis | {reply, agent_trace} | 危机完整话术（不流式） |
| error | {message} | 异常 |
| done | {reply, current_agent, agent_trace, ...} | 结束信号 |

### 10.3 流式编排流程

代码：chat.py L187-L377（`chat_stream`）

1. **triage 同步执行**（全规则路由，毫秒级，零 LLM）
2. **寒暄直达**：已产出 final_reply，直接推 token 后 close
3. **病例追问分支**：前端持有 case_context 时走轻量 `case_followup`（追问含危机词走 crisis 事件，否则走 token）
4. **危机路径**：escalation 不流式，推完整 crisis_message 后 close
5. **非危机路径**：
   - assessment（DB 查询 <100ms）
   - 提前推 sources（前端在 token 到来前先渲染知识卡片）
   - `stream_intervention()` 流式 yield token
6. **finally 写 assistant 轮**：保证客户端点「停止」时已生成片段也落库

### 10.4 流式质检策略

代码：intervention.py L385-L495（`stream_intervention`）

**为什么先缓冲再推**：token 一旦推给前端就无法撤回，流式质检后重试会造成"回复被替换"的 UI 闪烁。所以先收集完整回复，质检通过后再推出。

**为什么补推要匀速**：缓冲期间 token 瞬时到达，一次性 yield 前端会"整段闪现"丢失流式感。按 0.012 秒/字符匀速补推，恢复打字机效果（300 字回复约 3.6 秒）。

## 十三、高频 Q&A 深挖版

### Q1：为什么用 LangGraph，不自己写 if-else？

**主答**：对话链是有状态、有条件分支的 DAG。triage 后要根据 is_crisis、final_reply、默认三条路分流，状态（AgentState）在节点间传递。LangGraph 的 StateGraph + add_conditional_edges 天然表达这种结构，加节点只需要 add_node + add_edge，不动已有逻辑。

**追问：AgentState 里有什么？**
包含 user_message、history、triage_intent、is_crisis、final_reply、sources、agent_trace、node_decisions 等字段，节点返回的 dict 会合并到 state 中传给下一个节点。

**追问：如果要加一个"回访"节点怎么改？**
在 graph.py 里 `g.add_node("followup", followup_node)`，然后根据需要加边，比如 intervention → followup → END，或者加条件边。

### Q2：危机检测为什么要零 LLM 硬编码？

**主答**：心理危机是高风险场景，LLM 是概率性判断，可能漏判或延迟，漏判代价不可接受。硬编码关键词扫描是确定性的，秒级响应。代码在 safety.py，13 个关键词子串匹配，在 triage 节点最前面执行。

**追问：关键词不够全怎么办？**
关键词词表是安全基线，不是全部。LLM 意图分类里也有「危机」类别作为补充。但前置硬编码是底线，保证即使 LLM 误判也能兜住。后续可以扩充词表。

**追问：用户说"我觉得活着没意思"会命中吗？**
会，"没意义了"在词表里。"活着没意思"包含"没意思"但词表是"没意义了"，子串匹配不命中——这是当前词表的局限，可以补充。不过 LLM 意图分类会兜底。

### Q3：双版本部署怎么实现的？

**主答**：一个开关 LLM_MODE。cloud 走百炼 8 模型，local 全走 Ollama。代码在 llm.py，is_local 属性判断模式，model_for() 按角色返回对应模型名。local 模式下 dialog/report 可以挂各自的 LoRA 微调模型，留空回退基座。

**追问：两种模式的代码是同一套吗？**
是的，同一套代码。区别只在 model_for() 返回的模型名和 client 不同（百炼 client vs Ollama client）。Ollama 走 OpenAI 兼容端点，api_key 填占位非空值。

**追问：local 模式下语音也本地化了吗？**
语音 ASR/TTS 仍走百炼云端（faster-whisper + sherpa-onnx 本地化已实现但默认关闭），后续可切换。

### Q4：RAG 怎么保证检索不召回无关内容？

**主答**：两个机制。第一是场景标签过滤，每个知识文件有适用场景标签，非危机查询排除带危机标签的片段。第二是自适应阈值 + BM25 融合，云端 text-embedding-v3 阈值 0.75，本地 bge-m3 阈值 0.95（bge-m3 输出归一化向量，L2 距离分布不同），BM25 独有命中给虚拟距离 = 阈值 − 0.03。

**追问：阈值怎么定的？**
实测距离分布定的。bge-m3 归一化向量相关片段 L2 距离 0.77-0.91，无关 ≥1.10，所以阈值 0.95；text-embedding-v3 未归一化，0.75 合适。切换 embedding 模型后必须实测分布再定阈值。

**追问：切片策略是什么？**
结构感知切片。Markdown 标题作为章节前缀，过短段落合并，超长段落按句子边界二次切分。保证每片有头有尾。参数：MAX_CHUNK_CHARS=400，MIN_CHUNK_CHARS=40。

**追问：为什么不用 RRF 融合？**
RRF 让 BM25 关键词命中权重过大，「焦虑怎么缓解」中仅含"缓解"的科普片段会挤掉含具体做法的向量命中。向量语义相似度比关键词更能反映相关性。

**追问：怎么验证检索质量？**
65 条 query→expect 文件的评测护栏（`eval_rag.py`），recall@3 应 100%，32/32 文件覆盖。每次知识库扩充/改检索逻辑后必须重建索引 + 跑护栏，recall@3 下降即阻断。另有 433 条真实流量埋点日志，周度聚类无主题簇达 ≥5 次门槛。

### Q5：对话温度为什么设 0.6？

**主答**：实测调出来的。本地 LoRA 模型在 0.35 温度下会复读上一轮用户问句，升到 0.6 后自然度改善。但 intake 用 0.1 要确定性，报告用 0.1 要结构稳定（triage 已全规则化零 LLM，不再消耗温度配额）。

**追问：质检不合格重试时温度多少？**
三级阶梯：第一级 hint 保持 0.6（点名复读原句 + 上轮做法类别禁令）；第二级 rag_refresh 升到 0.7（换 RAG 检索片段重拼 prompt）；第三级 context_trim 也是 0.7（剔除历史 assistant 回复重拼）。不是简单降温，而是换上下文。

### Q6：反模板具体怎么做的？

**主答**：四层。Prompt 层 SAFETY_BASELINE 硬规则；质检层 check_reply_quality 检查闭合问句/复读/幻觉/做法多样性/长度；重试层三级阶梯（hint→rag_refresh→context_trim）；微调层 2979 条反模板语料重训。

**追问：check_reply_quality 检查哪些？**
闭合问句正则、问号不超过 1 个、长度 50-120 字、与历史无 ≥12 字公共片段（呼吸 4吸6呼 公式豁免）、「你说过X」中 X 在用户历史中、做法类别与上轮无交集、求做法问题 ≥2 种类别。

**追问：做法类别怎么定义的？**
6 类：breathing（呼吸）、journaling（写日记）、muscle_relax（肌肉放松）、mindfulness（正念）、exercise（运动）、planning（任务拆解）。同一种做法换说法算同一类，避免「腹式呼吸」和「手放肚子上呼吸」跨轮重复。

**追问：多轮对话质量怎么保证？**
eval_multiturn.py 4 场景×4 轮真实 LLM 走生产 HTTP 全链路，逐轮用生产 check_reply_quality 判定 + 跨轮复读/做法去重 + 求做法场景类别并集 ≥3。实测 15/16（≥90%，temp 0.6 ±1-2 轮波动），剩余 1 处为 LoRA 库存句（权重级限制）。

### Q7：量表计分为什么不交给 LLM？

**主答**：计分是确定性规则，LLM 算分可能出错且不可复现。四套量表都在 scales/ 下用 Python 规则实现，SDQ 有反向计分题，PHQ-A 第 9 题自杀意念单项直达升级。LLM 只负责把分数字段转成自然语言发展建议。

### Q8：数据安全怎么保证？

**主答**：三层。SQLite 文件权限 0600；备份用 openssl AES-256-CBC 加密；生产非 root 容器 uid 1000。另外匿名作答凭 6 位码，病例 PDF 不落盘只存元数据。

### Q9：云端 API 挂了怎么办？

**主答**：三级降级。百炼异常或空回复转 Ollama 本地（ollama_base_url 配置时），本地也失败走节点级硬编码兜底话术。流式只在未 yield 任何 token 时才切换。

### Q10：SSE 流式为什么要先缓冲再推？

**主答**：token 推给前端就无法撤回，流式质检后重试会造成"回复被替换"的 UI 闪烁。所以先收集完整回复，质检通过后再按 0.012 秒/字符匀速补推，恢复打字机效果。

### Q11：报告生成为什么要显式检查空回复？

**主答**：LLM 返回空字符串或纯空白不会抛异常，如果不检查就会生成空的发展建议。所以必须显式 `if not reply.strip()` 触发兜底。

### Q12：为什么改 .env 后要 docker compose up 而不是 restart？

**主答**：compose 的 env_file 变量在容器创建时注入，restart 不重读环境变量，必须 up -d 重建容器。这是 Docker Compose 的机制。

### Q13：多轮对话质量评测怎么做的？

**主答**：eval_multiturn.py 4 场景×4 轮（倾诉多轮延续/情绪跟进/话题切换/求做法后追问）走生产 `/api/chat` 全链路，逐轮累积 history。逐轮用生产 check_reply_quality 判定，场景级检查做法类别并集 ≥3。产物 latest.json + 时间戳归档，批次对比看 fixed/regressed 迁移。

### Q14：RAG 检索质量怎么持续监控？

**主答**：每次 search() 追加一行 JSON 到 `logs/rag_search_YYYYMMDD.jsonl`，记录 query/意图/阈值/top1 距离/是否放行/top3 文件tags。`analyze_rag_gaps.py` 周度聚类：信号①被过滤零命中、信号②放行但无做法型片段、信号③eval miss。同主题簇单周 ≥5 次立项补知识库。2026-10-01 实测 433 条流量 0 零命中。

## 十四、演示话术完整版

### 开场（30 秒）

各位老师好，我演示的是 PsycheFlow 智能心理评估系统，面向中小学校园心理筛查场景。核心能力有三个：标准化量表测评、AI 陪伴对话、智能报告生成。我从学生作答、AI 对话、危机处理、教师后台四个环节走一遍。

### 环节 1：门户与登录（30 秒）

这是三态门户，学生和教师入口零交叉。学生登录后进入首页，可以做量表、AI 对话、查看历史报告。教师登录后进入管理后台。

### 环节 2：量表测评与报告（90 秒）

我选 PHQ-A 青少年抑郁量表，共 9 题。做完提交后，系统用规则引擎计分，不交给 LLM，保证确定性和可复现。

报告对齐 MHT 六章节结构：测评工具介绍、解读注意事项、人员信息、测评结果（综合等级横幅 + 因子雷达图 + 尺度总览表）、逐因子剖析、发展建议。发展建议由 LLM 生成，但计分是规则。支持 PDF 导出。

注意这里的设计：计分用规则，叙事用 LLM，确定性和自然度兼顾。

### 环节 3：AI 对话（90 秒）

这是对话界面。我输入"怎么缓解焦虑"。

这里有个关键设计点：系统用硬编码正则识别"方法问句"，把意图从"求助"纠偏为"咨询"。为什么要纠偏？因为求助意图会跳过 RAG 检索，导致缓解方法的知识片段被拦截。纠偏为咨询后，RAG 才会检索放松技术、焦虑科普等知识片段。

回复带可折叠的知识来源卡片，默认不展开，避免干扰阅读。回复末尾最多一个开放式问题，禁止闭合问句。

我再输入"我最近压力很大，睡不着"。这是倾诉意图，系统先接住情绪，给一个具体做法（比如腹式呼吸 4 吸 6 呼），开放式收尾。

### 环节 4：危机处理（60 秒）

我输入"我不想活了"。

注意看响应速度——几乎是秒级返回。因为系统没有调 LLM，直接命中硬编码危机词表，输出 12355 青少年心理援助热线话术。这是安全前置原则：危机检测必须在所有 LLM 调用之前执行，不依赖模型概率判断。

同时系统会写 crisis_*.json 文件和 AuditLog 数据库表，双写留痕。

### 环节 5：教师后台（60 秒）

教师端可以用 CSV 名单建批次，系统生成 6 位筛查码，学生凭码匿名作答。批次详情页有危机名单和严重度分布，支持导出。

### 收尾（30 秒）

整个系统核心设计有两点：第一是安全前置，危机检测零 LLM 硬编码；第二是双版本部署，支持云端 API 和本地 Ollama 私有化切换，数据不出本机。我的演示完了，谢谢老师。

## 十五、改进方向与局限性

### 15.1 当前局限性

1. **危机关键词词表覆盖有限**：当前 14 个词，可能漏掉隐晦表达（如"我觉得活着没意思"中"没意思"未命中），依赖 LLM 兜底
2. **本地 LoRA 模型库存句**：7B Q4 量化模型能力有限，三级质检重试阶梯大幅缓解模板腔，但少量库存句（如 journaling「把担心的事写在纸上」）仍会跨轮复读，属权重级限制，需更多样化训练样本重训根治
3. **多轮对话温度波动**：多轮评测实测 15/16（≥90%），±1-2 轮属温度 0.6 正常波动，护栏看场景级通过率与 issue 分布趋势，场景级 4 过 3 为可接受线
4. **SQLite 并发瓶颈**：MVP 用 SQLite，规模化需迁移 PostgreSQL

### 15.2 可扩展方向

1. 扩充危机词表 + 引入语义危机检测（小模型二分类）
2. 增大微调语料多样性（dialog 2979→4000-6000），根治库存句复读
3. 知识库扩充到 40+ 文件，覆盖更多心理场景（躯体化/社交恐惧发言/家庭变故等）
4. SQLite → PostgreSQL，支持高并发批量筛查
5. 引入用户反馈闭环，持续优化对话质量
6. 统一 Qwen3-8B/Q5/DPO 路线（单模型替代三 LoRA，减少 8GB 显存换入换出）
